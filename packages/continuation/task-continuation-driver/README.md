# @deepseek-ai/dsh-task-continuation-driver

English | [中文](README.zh.md)

SQLite-backed provider for `ctx.taskContinuations`. The configured root contains a strict version-4 claim database. Provider startup opens and validates an existing database for cold recovery, but an empty deployment defers the `node:sqlite` import and database creation until the first reservation. Reads and terminal no-ops remain zero-write while no database exists. Before SQLite opens the database, the store walks from the filesystem root to the configured root with non-recursive directory creation. After either creating a component or observing `EEXIST` and confirming a directory, it flushes that component's parent before proceeding. A competing process killed between creation and its own flush therefore cannot leave an unflushed directory authority that another process accepts. Any required directory-sync failure rejects initialization. Windows alone accepts `EACCES`, `EINVAL`, `ENOTSUP`, or `EPERM` when Node cannot open or flush a directory handle; file fsync, SQLite `synchronous=FULL`, and every other failure remain mandatory. A failed open closes its SQLite handle and releases only that exact in-flight initialization, so a later recovery attempt in the same process can retry. Schema read, creation, and exact validation run under one `BEGIN IMMEDIATE`: failure rolls back application id, version, table, and indexes together. Validation requires the complete `table_xinfo` column metadata, canonical constrained `CREATE TABLE ... STRICT` SQL, primary-key index, caller/mutation unique index, no extra schema objects, and the exact state/revision relationship (`pending=0`, `ready=1`, `consumed=2`, `claimed=3`, or a reachable terminal revision). Every lifecycle mutation is one cross-process compare-and-set transition; unknown application ids, schema versions, schema objects, states, lease fields, or row fields fail closed. A winning transition persists `updatedAtMs` as the maximum of the requested, current, and creation timestamps, so a backward wall-clock step cannot violate the row constraint or strand the claim.

The lazy `node:sqlite` import suppresses only Node 22's exact SQLite `ExperimentalWarning`, so ordinary CLI stderr remains reserved for product diagnostics.

Calling `close()` terminalizes the store before it waits for the current in-flight initialization. An open that observes the terminal state closes its local SQLite handle before publication, and provider teardown awaits the store close after its earlier cleanup groups.

`verifierTimeoutMs` defaults to 30,000 and accepts integer milliseconds from 1 through 2,147,483,647. Each verifier receives a signal fused with that deadline and provider teardown. A timeout emits a warning, attempts the revision-fenced `pending` to `invalid` transition, removes the marker when that transition wins, and continues recovery with other Sessions; the timed-out claim is never dispatched. `recoveryRetryInitialMs` and `recoveryRetryMaxMs` default to 100 and 5,000; the maximum must be at least the initial delay. A resume, verifier, flush, scan, or cleanup exception schedules one coalesced exponential retry capped by the maximum. A verifier's explicit `not-ready` result is not a fault, but the claim remains subject to its durable expiry. `recoveryPollMs` defaults to 1,000. One earliest-due timer covers inactive-store discovery, cross-Host database advances, claim expiry, another owner's lease deadline, and fault retry; a failed explicit reservation cannot cancel that recovery schedule.

Creation first persists a pending record, then parks its fixed message with `agent.send(..., 'next-turn', false)` and checkpoints the Session. Caller-bound `reserve()` uses a unique `(callerId, mutationId)` key and the exact immutable payload, so concurrent and cold retries converge while different input fails. Calls with the same key in one provider share the complete park-and-checkpoint Promise: no replay returns before the winner's marker is durable, and a first-checkpoint failure invalidates the record before every participant receives the same rejection. Concurrent distinct-key reservations for one absent Session share one in-flight cold resume before each request revalidates its complete route and payload. Its closed cold-resume route accepts only provider and model identifiers of at most 256 UTF-8 bytes and an optional `maxTokens` from 1 through 1,000,000; live and caller-supplied routes are rejected before Agent resolution or claim persistence when they exceed those limits. Startup enumerates active records, resumes an absent exact Session, reconstructs the same dispatch message identity when clean Agent teardown removed its inbox, and invokes only the named verifier. A fully echoed positive decision becomes `ready`; after the inbox insertion is durable it becomes recoverable `consumed` intent. `dispatchLeaseMs` defaults to 30,000 and defines the renewable cross-process owner lifetime. Exactly one Host acquires an owner/incarnation lease before wake, renews it while downstream pre-step admission is blocked, and lets another Host take over only after expiry.

The pre-step fence calls downstream admission first and then requires its final batch to contain exactly one canonical continuation message before rechecking the exact lease, expiry, record revision, message identity, and direct-user task replacement across committed Session events, the claimed batch, and pending inbox work. Before it returns `enter` to AgentLoop, it performs a `synchronous=FULL`, owner/incarnation-fenced `consumed` to `claimed` CAS. Only that winner can reach the model, so dispatch is at-most-once across Hosts and restarts. A crash before the barrier permits takeover after lease expiry; a crash after the barrier may leave no continuation `user/message` event or model request, and recovery does not redeliver. A pre-existing exact dispatch event can still terminalize recovered `consumed` state without another turn. Public cancellation and supersession stop at `consumed`; the internal direct-user replacement fence may terminalize it before the barrier. Wrong session, revision, digest, verifier echo, expiry, cancellation, supersession, inbox content, duplicate continuation, lease, or newer direct-user message causes zero continuation dispatch.

Public list, cancellation, and supersession inputs are normalized and detached before the first asynchronous store operation, so later caller mutation cannot retarget a filter or transition. A cold-resumed `AgentHandle` belongs only to this provider: it remains registered while the Session has any `pending`, `ready`, or `consumed` claim, then is disposed exactly once after the last claim becomes terminal; caller-owned live handles are never disposed. Every cold resume receives a provider-lifetime creation signal, so teardown can cancel a stalled persistence load or setup before publication. Clean provider disposal aborts that signal and maintenance with `keepInbox`, cancels the due timer and lease heartbeats, then attempts every scan, probe, resume, lease, handle, and store cleanup and reports failures in operation order. A handle is removed from the ownership table only after successful disposal. Claim records retain the original Agent options but no task text; they are not deleted, so normal Agent teardown may clear its inbox without defeating pre-barrier recovery.

## Model Experience

### Recovered continuation turn

#### What the model sees

After the named verifier succeeds and the durable claimed barrier commits, a live process gives the model the fixed continuation message defined by `dsh-task-continuation` in one new turn. A crash in the following write-behind window may produce no turn. Store records, verifier payloads, CAS revisions, leases, and recovery diagnostics remain model-hidden.

#### Token effect

Each successful claimed dispatch adds one fixed user-role message and the ordinary assistant response generated for that turn. Recovery admits at most one copy; the post-barrier crash window may admit none.

#### KV Cache effect

The new turn appends after the persisted conversation prefix. Pre-barrier recovery reconstructs the same Session history and dispatch identity instead of copying the earlier task into a new prefix.

## Known Limitations and Deferred Work

- `claimed` proves only the durable pre-provider at-most-once barrier; it does not prove a Session event, model-provider call, or downstream side effect.
- Cold resume restores the claim's Agent options and persisted preset metadata; deployments that require extra resume-time composition must install that composition through the Agent factory.
