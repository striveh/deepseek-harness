# Agent Note: Complete Profile generation transactions

Status: implemented

English | [中文](2026-08-25-profile-generation-transactions.zh.md)

## Problem

A direct package-manager write can expose partially replaced Profile manifests, lock records, modules, archives, and patches to app boot. A lock alone serializes writers but does not hide those partial files from readers, recover a process killed during pointer publication, preserve the original live Profile, or prove that the selected tree actually boots.

The Extension Center also needs one mutation owner. A pre-Loader resolver is necessary to select the current tree, but it cannot serve runtime install/update/uninstall/configure requests inside the Web Loader. Conversely, a runtime Provider cannot change the tree already selected by its own process.

## Decision

[`dsh-profile-transactions`](../../../../packages/profile/profile-transactions/README.md) defines the lifecycle and branded state. [`dsh-profile-transactions-local`](../../../../packages/profile/profile-transactions-local/README.md) owns complete local generations, exact mutation admission, pnpm lock consistency, tree/content/revision fences, SQLite coordination, journal recovery, baseline capture, boot acknowledgement, and restore selection.

Each generation is a full Profile tree: manifest and ordered bundles, root patch, workspace and lockfile, retained local archives, and real package files. The local owner uses maintained `tar` and `yaml` packages. P0 accepts one exact `.tgz` install/update, installed-package uninstall, or installed-package-owned root-patch replacement. Numeric prerelease identifiers with leading zeroes are rejected. Compressed input and declared extracted content have independent 100 MiB limits; the copy path checks both initial size and observed bytes so a file that grows after `stat` also fails closed. Archives with dependencies, install lifecycle scripts, `bin` entries, unsafe paths/types, or mismatched name/version/digest fail before validation. For every package that is a current direct bundle or would become one through bundle install/update, the owner repeats app-boot's exact installation-anchor lookup and rejects an installation-resolved conflict before reservation, candidate creation, archive access, or validation; completed replay repeats the same ownership check. App-boot's installation-first resolution can therefore never substitute installation bytes for an admitted artifact. Archive-entry preflight and extraction keep separate cumulative entry/byte state, record callback rejection, and reject the owning Promise after the reader settles, so admission fails closed when the copied archive changes between passes without an uncaught callback error or a pending stage. Manifest and lockfile dependency mutation uses null-prototype maps and own-key membership, so legal Object prototype names cannot impersonate an installed owner or disappear during install. Configure carries current and next content digests plus normalized next UTF-8 bytes; the owner changes only `cordis.patch.yml` and does not parse YAML.

A CLI first install can precede ordinary Web Profile boot. Before the transaction owner reads its first snapshot, app-boot initializes the shipped Web template through flushed same-directory temporary files and atomic no-replace publication. A SQLite writer lease under the reserved transaction sibling serializes initializers and is released after process exit; PID-and-incarnation companion names distinguish live work from dead residue. Recovery completes only an exact subset of the four shipped template files, so concurrent initializers converge on complete template bytes while an interrupted prefix or any unrelated existing bytes fail without replacement and remain available for manual inspection. The CLI then heals the installation-owned `profiles/node_modules` fallback before stage, using the same app-boot resolution authority that later product launches use. The validator therefore exercises the standard base and Web rows rather than a reduced synthetic Profile.

Every request is fenced by both monotonic revision and a canonical digest of the effective tree. Stage and restore additionally require a caller mutation id. The Provider clones and recursively freezes mutation and transition requests synchronously before its first asynchronous store operation, so later caller writes cannot retarget a Profile, generation, mutation identity, or nested artifact input. A short SQLite transaction reserves each stage identity, archive construction and real Loader validation run without a held database transaction, and another short transaction finalizes the one generation. The current coordinator version is accepted only when its exact `STRICT` table SQL, complete column metadata, checks, and primary/unique indexes match. Exact concurrent or cold retries converge on one generation. Each building reservation binds the owner PID and exact OS process-creation identity, which first excludes process exit and PID reuse. Its exact stage Promise also holds an independent SQLite OS lock that contenders probe across Worker threads and processes. A live Worker and Promise retain the reservation; abnormal Worker termination releases the lease through the OS, so a later retry can replace it. An unfinished stage identity includes its initial fences. Once committed, the durable identity is Profile plus mutation id and semantic mutation, excluding newer fences and artifact transport paths; an equivalent retry returns the original generation and before/after receipt, while different semantic input under the same id fails. Staging copies the complete held tree, applies the exact change and owner-managed pnpm importer/package/snapshot records, verifies completeness, and invokes the local Provider's real Loader validator. The Service accepts no Consumer callback. A validator modification or failure removes the candidate. If stage work and reservation cleanup both fail, an ordered aggregate retains the stage failure first; retry can replace the reservation after its lease is no longer held. The first commit rechecks both fences under SQLite `BEGIN IMMEDIATE`.

The first commit captures the original live Profile as an immutable baseline and last-good target. If the live tree changes after capture or another pre-publication step fails, the owner removes the new baseline only after confirming that state and journal do not reference it, then flushes the generations directory. A committed candidate is active but pending restart. The CLI's short-lived bootstrap Context selects that active directory only after snapshot verifies every pointed immutable generation against its recorded tree digest. It copies the complete selected tree into an invocation-private runtime root through the Provider-owned copy primitive, verifies the private target against the selected digest, loads the Profile from that copy, and confirms the same snapshot again. Only the private copy becomes Loader's explicit base; a source edit before or during preparation fails a digest or snapshot fence, while a later source replacement cannot supply imported plugin bytes. The same runtime root owns launcher `cordis.yml` and is released on boot failure or app disposal. Its name binds the owner PID and exact process-incarnation fingerprint, so later preparation deletes SIGKILL residue and PID-reuse residue while preserving live sibling invocations. The CLI acknowledges the exact authoritative generation only after real Loader activation. That acknowledgement promotes it to last-good and moves the former last-good to rollback. Restore selects last-good for an unverified active generation and rollback after verification.

The CLI and runtime deliberately mount two `LocalProfileTransactions` instances over the same `profilesDir`. The bootstrap instance exists only around resolution and acknowledgement. The `dsh-base` instance serves runtime Extension Center requests that affect the next process. SQLite supplies cross-process exclusion; neither instance retains a lock between calls, and a runtime commit never changes its process's effective directory.

Managed generation patch files are not re-read or watched by Profile HMR. The home patch stays live. Configuration changes to a managed Profile must pass through configure staging and real candidate validation; an external generation edit instead fails the next tree fence.

Pointer transition intent is durably written to `journal.json` before state replacement. Commit and restore retain that correlated journal until SQLite holds the caller key, semantic digest, and exact before/after receipt. A process killed after journal fsync, including after state fsync but before receipt persistence, recovers the same receipt before cleanup; retry returns the original generation and transition without incrementing revision or applying the mutation again. A real process death releases the SQLite reservation. Read-only snapshot/list project a valid journal without clearing it; the next writer completes the transition when state equals `before`, accepts it when state equals `after`, and rejects every unrelated relationship. Before creating or accepting `writer.sqlite`, the owner walks from the filesystem root to `.dsh-profile-transactions/<profile>/generations` with non-recursive directory creation. It fsyncs each component's parent after either creation or `EEXIST` plus directory confirmation, so a competing writer killed before its own fsync cannot publish authority that another writer accepts. Any required parent-directory fsync failure aborts before coordinator admission. State, records, and every supported file and directory in a generation are flushed before publication.

The public restore-receipt query takes the same writer reservation and completes a correlated retained journal before looking up the exact Profile plus caller mutation id. A committed result carries the terminal status and original before/after snapshots; absence does not initialize a Profile or select another target. This lets an external recovery Consumer distinguish a lost response from an unstarted restore before it evaluates the now-changed recovery selector.

## Validation ownership

The local Provider uses the product CLI's hidden argv route to spawn a detached, bounded child for candidate admission. The child loads the staged Profile read-only, composes real patches, boots the real Web Loader on `127.0.0.1` with port zero, then disposes. The configured `validationTimeoutMs` bounds activation and disposal within Node's schedulable timer range. The parent settles from child `close` after stdio drains. When Unix process-group kill or Windows `taskkill` fails during output-limit or timeout handling, the parent first marks the operation settled, destroys both stdio pipes, and unreferences the child. The original validation failure remains first in the ordered aggregate, followed by independent termination and local-release failures; a surviving child cannot retain the launcher's event loop. The child awaits disposal before unconditionally removing the validation home; independent validation, disposal, and removal failures retain their order in an aggregate rather than starving a later cleanup. Its synthetic root file lives under the disposable validation home, while an explicit Loader base URL stays anchored to the candidate Profile root; validation therefore leaves candidate bytes unchanged without breaking relative entry semantics. Parent-side timeout, output bounds, and process-tree termination contain failed plugins. The child inherits only process-launch, locale, and temporary-directory names, then replaces home, Harness-home, XDG, application-data, and temporary roots with a disposable directory. Credential-shaped names, credential-file pointers, provider endpoints, proxies, SSH-agent authority, Node injection options, and all other ambient names are absent. P0 intentionally rejects non-Web candidates until another real activation adapter exists.

Environment minimization and loopback binding are not a filesystem or network sandbox. Candidate plugin code has already crossed trust admission and executes with the host user's operating-system authority during validation. A Consumer must complete provenance policy and human approval before it asks the transaction owner to stage that code.

## Alternatives considered

**Mutate the live Profile under one lock.** Readers can still observe a partial multi-file graph, and rollback must reconstruct overwritten state.

**Keep package-manager mutation in `dsh plugin`.** It bypasses the shared SQLite owner, exact artifact admission, tree fences, journal, validation, and recovery semantics used by the Extension Center.

**Store only a pointer or package manifest.** Boot needs a complete package tree and a lockfile consistent with real installed files; reconstructing either during restart reintroduces partial mutation.

**Treat commit as success and last-good.** Commit proves durable selection, not that Loader activation succeeds. The separate acknowledgement preserves a known recovery target across a failed restart.

**Let the temporary Loader root choose the resolution base.** Relative plugin names and configuration paths would resolve from the invocation's temporary directory. A private root plus the effective Profile's explicit base keeps runtime files outside managed content without changing Profile semantics.

## Consequences

The P0 archive restrictions are intentionally narrower than npm. Packages requiring regular dependencies, lifecycle installation scripts, or executable shims fail loud. Multi-package graph changes and automatic retention pruning remain future work.

The active pointer changes only after validation, and the running process changes only after restart. A failed or killed publication has deterministic recovery; a failed Loader boot does not overwrite last-good. Snapshot and list remain zero-write operations even before any transaction store exists.

The restore-journal SIGKILL case first queries the public receipt after restart, then replays the same restore id and proves the Profile revision remains unchanged.

Focused acceptance covers exact install/update/uninstall/restore across cold provider starts, completed install/update/configure/uninstall replay across newer fences without another validation or revision, first install of packed ordinary and `constructor` packages into the standard Web template under a fresh isolated Harness home, custom direct-bundle conflicts resolved from the exact installation anchor before reservation, caller-request detachment, concurrent same-key staging, different-input key conflicts, active generation correlation, pnpm lock updates, symmetric bundle-to-package and package-to-bundle updates, own-key installed-owner checks, patch content and whole-tree conflicts, external edits, rejected archives and validators, ordered validator disposal and removal failures, first-baseline recovery, active generation Loader boot with a relative entry, managed-patch HMR exclusion, cross-process stale commits, real `SIGKILL` windows after stage reservation, generation persistence, commit state fsync, and restore journal persistence, and real child Loader activation without inherited credential, credential-file, endpoint, proxy, or SSH-agent environment authority.
