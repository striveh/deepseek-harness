# Agent Note: Extension-management Host owners

Status: implemented

English | [中文](2026-08-25-extension-management-host-owners.zh.md)

## Problem

A lifecycle product cannot safely emulate extension ownership by editing live Profile YAML, mounting an MCP client behind published desired state, or re-sending raw task text after a restart. Those shortcuts split authority between the product and runtime, lose optimistic conflict detection, and cannot prove teardown or durable dispatch identity.

Plugin, MCP, and continuation support also cannot be represented by one availability boolean. A Store may remain readable when one owner is absent, but partial support is not an `installed` or `acquisition available` state. Task-driven acquisition needs to distinguish all three because a selected candidate may change a Profile, create an MCP connection, or require the original task to survive a restart.

## Decision

DSH publishes three product-neutral Host capabilities required by lifecycle managers: immutable Profile generation transactions on `ctx.profileTransactions`, durable dynamic MCP desired state on `ctx.mcpConnections`, and verifier-gated cross-restart task continuation on `ctx.taskContinuations`. The shipped base bundle mounts their local providers. An out-of-tree Extension Center consumes these APIs through normal package peers and Cordis injection; DSH does not embed its catalog, policy, plans, browser workflow, or extension ownership records.

Each owner is independently revisioned and durable, and exposes literal `protocolVersion: 1` in addition to its Service class identity. Profile mutations bind caller ids, stage a complete immutable generation before publication, and retain a named last-good generation. Each building stage binds the owner PID plus exact OS process-creation identity, then holds an independent SQLite OS lock for the exact stage Promise. Contenders probe that lease across Worker threads and processes: a live Worker retains its reservation, while abnormal Worker termination releases the lease through the OS and permits a later retry to replace it. Before coordinator admission, the Profile owner walks from the filesystem root through the transaction ancestry with non-recursive directory creation and parent-fsyncs every component after either creation or `EEXIST` plus directory confirmation. First execution is revision/tree fenced; after commit, an equivalent completed identity returns its original generation and before/after receipt across newer fences without another validation or revision. Commit and restore retain correlated journals until SQLite holds the exact receipt, so recovery after state fsync completes that identity instead of republishing it. MCP operations persist one exact descriptor, reserve their Tool namespace against unmanaged collisions, and wait for the ordinary MCP client Fiber to publish or withdraw its owned Tool generation; permanent deletion is a separate revision-fenced purge of an already removed record. Every MCP read-repair-write cycle runs under a SQLite `BEGIN IMMEDIATE` reservation with a bounded wait, so process death releases cross-process ownership without an orphan pathname lock. Streamable HTTP descriptors carry an explicit Fetch redirect policy through the desired-state owner into the SDK transport. The Extension Center admits `redirect: "error"`, so an endpoint cannot redirect a reviewed zero-secret request to another location. Continuation reservations bind branded task-revision and verifier identities, a caller mutation key, one original direct-user message, evidence digest, restricted cold-resume route, dispatch identity, and expiry. Same-key calls in one provider share the complete marker checkpoint result; distinct-key reservations for one absent Session share one provider-lifetime-cancelable Agent resume before each caller's complete input is revalidated. Before opening SQLite, the version-4 owner walks from the filesystem root to the configured store root with non-recursive directory creation and parent-fsyncs every component after either creation or `EEXIST` plus directory confirmation. It then validates the exact constrained `STRICT` schema, dispatch-lease columns, and fixed state/revision relationship under one `BEGIN IMMEDIATE`. Only documented Windows directory-handle errors are exempted. A failed open closes its SQLite handle and releases the exact failed initialization so in-process recovery can retry. One Host must hold a renewable owner/incarnation lease before wake. After downstream pre-step admission returns exactly one canonical continuation message, the same owner commits a `synchronous=FULL` `consumed` to `claimed` barrier before AgentLoop may invoke the model. A pre-barrier crash permits takeover after lease expiry; a post-barrier crash may produce neither a continuation event nor a provider request and is never automatically redelivered. One earliest-due timer covers inactive-store discovery, cross-Host advances, claim expiry, lease takeover, and bounded fault retry. Provider-owned cold handles remain registered through the Session's last active claim and are then disposed exactly once; teardown aborts stalled creation and attempts every cleanup without discarding the primary failure.

Continuation store close is terminal. It marks the instance closed before draining the current opening Promise, and an open that observes the terminal state closes its local SQLite handle before publication. Provider teardown awaits this close after its earlier cleanup groups, so close failures retain their final operation-order position.

## Composition and limits

`dsh-base` mounts the three local providers for every shipped Profile. The Profile owner is mounted twice: a short-lived CLI bootstrap instance resolves and acknowledges the tree used by the current process, while the base instance accepts runtime requests for the next process. Each CLI invocation mounts its Loader from a private launcher-owned root file whose relative-entry base remains the selected Profile, so sibling launches and Loader write-back never mutate an immutable generation. Disabling a row through a later Profile patch withdraws that owner and makes dependent products report `unavailable(host-capability)`.

## Verification

The CLI filters only Node 22's exact experimental SQLite warning so lifecycle owners do not pollute product stderr. A missing custom Profile reports the exact transactional install command instead of exposing only its directory prerequisite.

Package tests cover CAS conflicts, wall-clock rollback, concurrent caller-key idempotency through the first marker-checkpoint failure, staging-reservation and restore-journal process death, corruption recovery, MCP writer process death and subsequent recovery, quiescent MCP teardown, unmanaged Tool namespace collisions, real stdio and HTTP Tool generations, cancellation before consumed intent, bounded and teardown-aborted verifier races, stalled-verifier isolation across Sessions, post-listener expiry and duplicate rejection, committed, claimed-batch, and pending-inbox newer-user supersession, strict continuation schema tampering, first-root durability faults including a competing creator, failed-open in-process retry, pre-barrier lease takeover across two Hosts, the post-barrier kill window, cold-handle ownership, automatic retry and expiry without external events, and stalled-resume teardown. Protocol probes reject same-name fakes and wrong revisions. The base bundle config gate proves the providers are resolvable from the published dependency closure. The independent Extension Center owns the final packed browser, Profile restart, provider lifecycle, and original-task convergence scenario.

The continuation lifecycle suite also pins terminal close during an in-flight open, local-handle release before publication, propagation of a concurrent real open fault, and driver waiting with ordered close-failure aggregation.

## Alternatives considered

**Let the Extension Center edit or dispatch through lower-level primitives.** Direct Profile writes, private MCP Fibers, and raw task replay bypass the only components that can enforce whole-tree, namespace, and dispatch-evidence invariants across process death.

**Put all lifecycle state in one Extension Center-specific Host service.** That couples DSH to one catalog and UI product, prevents CLI and automation consumers from sharing the mutation owners, and makes the three durability models evolve together.

**Probe only method names or publish one aggregate capability flag.** A same-name fake or incompatible revision can be mistaken for an owner, while one flag hides which lifecycle can actually mutate, verify, recover, or continue.

## Consequences

Product-neutral owners keep mutations behind the same APIs used by CLI, UI, and automation consumers while the Extension Center remains an independent project. The cost is three separately durable services, three protocol probes, and explicit partial-availability handling in every lifecycle product. A verifier deadline deliberately prefers an `invalid` false negative over starving recovery for every Session; deployments with slower bounded verification must raise the configured deadline.

These services grant no package, network, credential, or model authority by themselves. They accept exact caller inputs, enforce revisions and durability, and expose evidence. The consuming product still owns source admission, artifact integrity, human approval, credential references, operation receipts, and recovery policy. A successful MCP handshake is not a security review; a booted Profile is not proof of every Plugin behavior; a resumed task is not proof that its user-visible goal succeeded.
